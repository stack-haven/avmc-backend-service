## 一、正确性与语义一致性 —— 4/10 🔴

### C1【P0】`Pipeline.Run(ctx, nil)` panic 逃逸

`pipeline.go` 的 `defer` 里先 `recover()`、再调 `p.finalize(ec)`。
`ec == nil` 的检查发生在 defer 注册**之后**，且 `finalize` 在 recover 之后执行，
一旦 `finalize` 自己 panic，**没有第二层 recover 能兜住**。

```text
=== RUN   TestAudit_NilEC
    FINDING nil-ec panic escapes Run: runtime error: invalid memory address or nil pointer dereference
```

宣称的「HA 三重保护」在最基础的 nil 输入上就失效。

### C2【P0】Policy 阈值是死代码

`Policy.PinyinThreshold / FuzzyAutoThreshold / FuzzySuggestThreshold` 三个字段
**从未传给任何 processor**。`builder.go` 调的是 `reg.Build(name)`——不带 opts：

```go
proc, err := reg.Build(name)   // ← opts 永远为空
```

阈值只在 `builtins.go` 里被**硬编码**（`WithCategoryAutoThreshold("PERSON", 0.65)`）。
用户改 Policy 无任何效果，属于「静默无效配置」，是最危险的一类 API 缺陷。

### C3【P0】`fuzzy_matching` 用陈旧窗口扫描已被修改的文本

```go
text := ec.Text
runes := []rune(text)          // 快照一次
...
ec.Text = replaceAll(ec.Text, sub, stdText)   // 循环内不断改 ec.Text
```

`runes` 来自进入时的文本，替换发生后长度/内容已变，
后续窗口 `runes[i:i+n]` 与 `ec.Text` 的实际内容**不再对应**。
当替换导致长度变化时会产生错位替换或幽灵 Change。

### C4【P0】单次调用产出 4009 条 Change

45 字的句子 + 2000 词条，输出：

```text
status=SUCCESS elapsed=57.7ms lockedSpans=4 changes=4009
```

`fuzzy_matching` 对每个 `SUGGEST` 都无条件 append 一条 Change，无 top-K、无去重、无上限。
这既是内存放大，也让调用方拿到不可用的结果（真正的替换只有 4 条）。

### C5【P1】`clampThreshold` 越界回落到 **0** 而非默认值

```go
if v < 0 || v > 1 { return 0, errs }   // 注释说 fallback，实际是归零
```

`fuzzy` 阈值为 0 意味着 `conf >= 0` 恒真 → **全部自动替换**。
一个配置笔误会把「保守建议」变成「无差别改写」。这是埋在库里的地雷。

### C6【P1】空 `EnabledProcessors` 的语义与文档相反

`policy.go` 注释：「空切片 = 不启用任何 processor（= noop Pipeline）」
实测：

```text
FINDING empty EnabledProcessors -> [cleaning filler vocab_matching ... context_correction]
```

`normalizeOrder` 把空列表还原成了全量默认。文档与行为 180° 相反。

### C7【P1】`filler.WithStrongFillers` 对多字口水词静默失效

`Process` 是 **逐 rune** 匹配（`key := string(r)`），
用户传入 `"那个"`、`"然后"` 这类多字口水词永远不会命中，且无任何报错。

### C8【P1】`pinyin_correction` 注入的 `PinyinService` 从未被使用

`Processor.pinyinSvc`、`autoThreshold` 声明并注入，但 `Process` 里只做了
`HOMOPHONE` 关系的字符串替换，**一次拼音都没算**。
`processors/common.go` 为此依赖 `backend-service/pkg/pinyin`——一条纯粹的死依赖。

### C9【P2】`LockedSpans` 名不副实

它是 `[]string`（字符串集合），不是 span（区间）。后果：
- 锁定 `"周丽群"` 会锁住文本中**所有**位置的该子串，无法只锁某一处；
- `Lock` 无去重，同一词重复 append：

```text
FINDING LockedSpans dup grows: [同一个词 同一个词 同一个词 同一个词 同一个词]
```

- `IsLocked` 是 O(n) 线性扫描，配合无界增长 → O(n²)。

### C10【P2】`Change` 无位置信息

`Change{From, To, Action, ...}` 没有 offset，调用方无法做高亮/diff/撤销，
也无法判断「同一个词的第 2 次出现」。作为公开库这是硬伤。

### C11【P2】编译期断言是噪声/无意义

```go
var _ TextProcessor = (TextProcessor)(nil)   // processor.go：恒真，无断言价值
var _ = context.Background                    // context.go：为了保住 import
var _ sync.Mutex = sync.Mutex{}               // observer.go：同上
_ = time.Now()                                // observer.go SnapshotOf 内的死代码
```

### C12【P2】`ObservingProcessor` 丢弃原始 panic

```go
if innerPanic { panic("re-panic from ObservingProcessor") }
```

原始 panic value 与调用栈全部丢失，线上排障时只能看到这句无信息量的字符串。

## 二、API 设计与易用性 —— 4/10 🔴

### A1【P0】没有 Facade，最小可用路径过长

当前用户必须理解 5 个概念才能跑通一次增强：

```go
reg := builtins.NewDefaultRegistry()
policy := textenhance.DefaultPolicy()
pipeline, _ := textenhance.BuildPipeline(reg, policy)
ec := textenhance.NewEnhancementContext(text, vocab, policy)
pipeline.Run(ctx, ec)
result := ec.Text          // ← 从入参结构体上读结果
```

开源库应该是 `New` + `Enhance` 两步。当前形态对新用户不友好，
也让 API 演进被死死锁住（所有中间类型都已导出）。

### A2【P0】以「可变入参」返回结果，违反 Go 惯例

`Run(ctx, ec)` 不返回任何值，结果从 `ec` 的导出字段读。
应返回 `(Result, error)` 这样的不可变值。

### A3【P0】不可变承诺全部落空

- `VocabularySnapshot.Entries / Relations` 是**导出的 map**，调用方可随意改写「不可变快照」；
- `Policy` 声称「构造后不可变」，但所有字段导出可写；
- `EnhancementContext.Text / Changes / LockedSpans` 导出且被 processor 直接赋值。

### A4【P1】`Option = any` 放弃类型安全

```go
type Option = any
func ToOptions[T any](opts []Option) ([]T, error)
```

配置错误从编译期推迟到运行期。而且 `BuildPipeline` 根本没有把 opts 透传下去（见 C2），
Registry 目前**严格劣于直接调用 `New`**，没有创造任何价值。

### A5【P1】`Processor.Process` 不返回 error

强制每个实现者自己做 HA（`if ec == nil` / `select ctx.Done()` / 累积 error），
9 个 processor 复制粘贴了 9 遍同样的样板。错误处理策略应属于 Pipeline，不属于 Strategy。

### A6【P1】Observer 接口有 6 个方法，实现成本高

没有 `BaseObserver` 可嵌入，用户想只监听一个事件也必须实现 6 个方法。

### A7【P2】`defaultPipelineTimeout = 5s` 无法关闭

库擅自给没有 deadline 的 ctx 加 5s 超时，且不提供关闭开关。
批处理/离线场景会被静默截断为 `CANCELED`。

### A8【P2】业务数据硬编码进「框架」

```go
{From: "个种籽", To: "颗种籽"}                       // phrase_standardization 默认规则
{From: "功课", Context: "技术难点", To: "攻克"}       // context_correction 默认规则
WithCategoryAutoThreshold("PERSON", 0.65)            // builtins 硬编码
```

开源库的默认值里出现「种籽」「攻克技术难点」，语义上不可解释。

## 三、性能与算法 —— 3/10 🔴

### 基准（2000 词条 + 2000 关系，45 字中文句）

```text
BenchmarkAudit_Pipeline-16   20   48,768,761 ns/op   11,451,777 B/op   227,859 allocs/op
```

**48.7 ms / 单句、11.4 MB 分配、22.8 万次 allocation。**
按 ASR 实时增强场景（每秒数百句）估算，单机吞吐 < 20 QPS，且 GC 压力极大。

### 逐 processor 耗时

| processor | 耗时 | 根因 |
|---|---:|---|
| fuzzy_matching | 30.2 ms | O(E × N × L) 滑窗 + 每窗口 `string(runes[i:i+n])` 分配 |
| alias_resolution | 26.4 ms | `resolveTarget` 对每条 relation 全表线性扫 Entries → O(R × E) |
| vocab_matching | 438 µs | 每次 Process 重新 `sortedEntryKeys` 排序 + E 次 `strings.Contains` |
| deterministic_replacement | 186 µs | 同 alias，O(R × E) |
| pinyin_correction | 152 µs | 同上 |

### 关键算法问题

- **P1 缺 ID 索引**：`resolveTarget` 是 O(E) 全表扫描，而 `TargetEntryID → Entry` 本应是 O(1) map。三个 processor 各抄了一份同样的错误实现。
- **P1 多模式匹配用了 E 次单模式扫描**：`for entry { strings.Contains(text, entry) }`。
  正解是构建一次 **Aho–Corasick 自动机**，O(N + matches)，与词条数无关。
- **P1 每请求重复排序**：`sortedEntryKeys` / `sort.Slice(sortedEntries)` 在**每次 Process** 里跑。
  确定性顺序应在 Snapshot 构建时固化一次。
- **P1 `strings.ReplaceAll` 逐规则全文重扫**：R 条规则 = R 次全文遍历，且存在级联替换
  （A→B 后 B 又被 B→C 命中）。正解是单次左到右扫描 + 最长匹配优先 + 冲突消解。
- **P2 fuzzy 无候选剪枝**：对每个词条在全文滑窗算 Levenshtein。
  应先用 n-gram 倒排 / BK-tree 剪掉 99% 候选。
- **P2 `IsLocked` O(n) + 无界 append** → O(n²)。
- **P2 `filler` 每次 Process 重建 matchSet**，构造期就该建好。

## 四、并发与内存安全 —— 3/10 🔴

### S1【P0】「线程安全」是可复现的谎言

`EnhancementContext` 带 `sync.Mutex` 并宣称线程安全，
但 9 个 processor **全部绕过锁直接赋值**：`ec.Changes = append(ec.Changes, ...)`、`ec.Text = ...`。

`go test -race` 实测：

```text
WARNING: DATA RACE
Read at 0x00c0000e65b8 by goroutine 9:
  .../processors/cleaning.(*Processor).Process()  cleaning.go:108
Previous write at 0x00c0000e65b8 by goroutine 10:
  .../processors.(*EnhancementContext).appendChange()  context.go:63
```

**结论**：要么真正封装（字段私有 + 全部走方法），要么明确文档化为「单 goroutine 独占」并删掉 mutex 制造的虚假安全感。当前是最坏的第三种：有锁、有承诺、无保护。

### S2【P1】`Status int32` 读写无同步

`GetStatus/SetStatus` 是裸字段访问，未走 mutex 也未用 `atomic`。

### S3【P2】无输入规模上限

文本长度、词条数量均无上限。`fuzzy_matching` 的 O(E×N×L) 遇到超长输入即为 DoS 向量。

### S4【P2】日志泄露原文

`LoggingObserver.OnPipelineComplete` 直接打印 `text=%q→%q` 全文。
ASR 场景下这是 PII，开源库默认不应打印内容，需提供脱敏钩子。

## 五、可扩展性 / 设计模式落地 —— 6/10 🟡

**做对的部分**（应保留）：
- Strategy（`TextProcessor`）职责单一、边界清晰；
- Functional Options 在每个 processor 子包一致落地；
- Registry / builtins 分包成功规避了 import cycle，思路正确；
- Observer + Decorator 的分层意图正确。

**问题**：
- 存在 **三套并行的横切机制**（Pipeline 内联 recover/计时 + ObservingProcessor Decorator + Notify* 函数），
  职责重叠：`runOneStep` 和 `ObservingProcessor` 各计一次时。应统一为 **Middleware 链**；
- Decorator 只被 `BuildPipeline` 内部使用，用户无法自定义装饰器顺序；
- Registry 不能透传 Option（C2），插件协议缺失，第三方无法通过配置文件注册 processor；
- `llm_reserved` 是空壳 + 一大段注释掉的伪代码，不应出现在开源版本。
