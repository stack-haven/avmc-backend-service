> 中文名：文本词法规范引擎（简称：**文本规范引擎**）
> Module：`github.com/ark/lexnorm`
> 版本：v0.1（能力定义基线）
> 状态：待架构与代码落地

---

## 0. 一句话定位

> **ark-lexnorm** 是一个**可由用户自定义处理项、按确定性递减顺序执行的文本词法规范引擎**——
> 输入一段含噪声/口水词/别名/错字/同音字/近似字/上下文错误/语法错误的原始文本，
> 经过**「噪音清洗 → 口水词处理 → 词库别名替换 → 确定性替换 → 拼音纠正 → 模糊纠正 → 上下文纠错 → LLM 大模型语法纠正」**的规范化流水线，
> 输出**规范文本**。
> 引擎在流水线启动前会预缓存词库、词条、别名映射、确定性纠错词、同音词、近似词等所有词法规范因子，
> 以保证运行期处理性能与一致性。

> 三个不可妥协的属性：**受控（controlled）** · **确定（deterministic）** · **可解释（explainable）**。

---

## 1. 核心命题（第一性原理）

> 文本改写的风险，与「所依据知识的确定性」成反比。
> 因此：**改写必须按知识确定性降序执行，高确定性的结论不可被低确定性的推断推翻**。

它同时决定了三件事：
- 流水线的执行顺序
- 保护区（Protected span）机制的必要性
- 第三方扩展如何声明自己在流水线中的位置

---

## 2. 内置流水线（默认 8 步，按确定性降序）

| # | 步骤 | 确定性 | 典型动作 |
|:--:|---|:--:|---|
| 1 | **噪音清洗** Normalize | 1.0 | 控制字符、不可见空白、重复标点 |
| 2 | **口水词处理** Disfluency | 1.0 | 删除「呃/额/啊/那个/然后」等不流畅成分 |
| 3 | **词库别名替换** Alias Map | 1.0 | 已登记别名 → 标准词（按词库 Term 表） |
| 4 | **确定性替换** Deterministic Map | 1.0 | 已登记纠错 → 标准词（按词库 Correction 表） |
| 5 | **拼音纠正** Pinyin Correction | 高 | 同音字 → 标准词（按词库 Homophone 表 + 拼音索引） |
| 6 | **模糊纠正** Fuzzy Correction | 中 | 编辑距离命中 → 标准词（按类别阈值） |
| 7 | **上下文纠错** Contextual Correction | 中 | 上下文规则 → 标准词（按词库 Context 规则） |
| 8 | **LLM 大模型语法纠正** LLM Refine | 未知 | 仅在用户启用 LLM 时插入；可选语法改写 |

**为什么是这个顺序**：从「无知识」（1、2）到「确定性映射」（3、4）到「统计性推断」（5、6、7）到「开放模型」（8）。
高确定性步骤先把能确定的改对、并把它们**锁住**（保护区），
后续步骤只对未保护区域做推断——保证不会出现「先猜对后被改错」。

> 这 8 步**每一项都是默认开启**；但用户可以在调用前**禁用任意一项**或**插入自定义处理项**。
> 也可选择只跑前 N 步（例如「只要确定性替换」跑完就返回）。

## 3. 用户调用模型

```
           ┌──────────────────────────────────┐
           │  Profile（词表 + 策略具名绑定）   │
           └──────────────────────────────────┘
                        ▲
   ┌────────────────────┴────────────────────┐
   │                                         │
 Lexicon (Term / Variant / Rule / Pinyin /    │
          Similar) — 引擎启动期/热替换期预缓存  │
   │                                         │
   └────────────────────┬────────────────────┘
                        ▼
   ┌──────────────────────────────────────────┐
   │  Engine.Enhance(ctx, profile, text, opts)│
   │  ├── opts.Configure(steps...)?  // 自定义│
   │  └── → Result{Text, Changes, Status...}  │
   └──────────────────────────────────────────┘
                        │
                        ▼
                  规范文本（Result.Text）
```

### 3.1 调用前可自定义的项

- **启用哪几步**（可禁用、可插入用户自定义 Processor）
- **每步的阈值**（如模糊纠正的编辑距离上限、类别相关阈值）
- **是否启用 LLM**（步骤 8，可整体开关 + 端点/超时/提示词模板配置）
- **保护区初始集合**（用户预先告诉引擎「这几个区间不动」）
- **决策阈值**（什么置信度以上自动 Apply，之下走 Suggest）

### 3.2 引擎预缓存的词法规范因子

为避免运行期重复构建，引擎在启动期（以及词表热替换时）一次性预缓存：

| 因子 | 数据来源 | 用途 |
|---|---|---|
| 词条倒排 | Lexicon.Terms | 精确 / 模糊查找入口 |
| 别名映射 | Lexicon.Aliases | 步骤 3 |
| 确定性纠错映射 | Lexicon.Corrections | 步骤 4 |
| 同音词索引 | Lexicon.Homophones + 拼音字典 | 步骤 5 |
| 近似词索引（n-gram 倒排 / BK-tree） | Lexicon.Terms | 步骤 6 |
| 上下文规则表 | Lexicon.ContextRules | 步骤 7 |
| 类别阈值表 | Lexicon.ClassPolicy | 步骤 6、7 的分流 |
| Aho–Corasick 自动机 | 全部已登记变体 | 多模式匹配加速 |

> 缓存一旦构建，**运行期只读**；更新通过 `Engine.UpdateProfile()` 走 atomic swap，不阻塞调用方。

## 4. 概念去业务化对照表

包内**禁止**出现业务词。本表是命名与命名空间的硬约束：

| 业务词（原代码） | 通用词（本包） | 说明 |
|---|---|---|
| 多租户 / tenantID | **Profile** | 词表 + 策略的具名绑定；多租户只是 Profile key = tenant id 的特例 |
| 私有词库 / 系统词库 | **Lexicon** | 纯数据结构：Terms + Variants + ClassPolicy + ContextRules |
| 词条 / 标准词 | **Term** / **Canonical form** | |
| 别名 / 纠错 / 同音 | **Variant**（带 `VariantKind`） | ALIAS / CORRECTION / HOMOPHONE 三者本质同构 |
| 口水词 | **Disfluency** | 通用 NLP 术语 |
| ASR 错字 | **Approximate variant** | 包不应知道错误来源 |
| 锁定片段 LockedSpans | **Protected span** | 「已确定，禁止下游改写」的语义 |
| 增强 / Enhance | **Normalize** / **Correct** | "enhance" 语义模糊且暗示不可验证的承诺 |
| PERSON/ORG 分类阈值 | **Class** + per-class policy | 类别是开放字符串 |

> 结论：包内**不应出现** `tenant` / `ASR` / `词库` / `租户` / `口水词` / `专名` 任何一个词。
> `Profile` + `Lexicon` + `Term/Variant` + `Protected span` + `Class` 是完整的替代集。

## 5. 六项原子能力（对外承诺）

| # | 能力 | 说明 |
|:--:|---|---|
| 1 | **Canonicalization** 归一 | Variant → Canonical，单次扫描、最长匹配优先、冲突可消解 |
| 2 | **Approximate Matching** 近似匹配 | 编辑距离 + 类别阈值，对未登记变体做收敛 |
| 3 | **Protection** 保护区 | 已确定区间禁止下游改写，保证单调收敛 |
| 4 | **Decision Grading** 决策分级 | Apply / Suggest / Skip 三档，按置信度与类别策略分流 |
| 5 | **Provenance** 溯源可解释 | 每处改动记录 from/to/位置/依据/来源/置信度/是否生效 |
| 6 | **Determinism** 确定性 | 同输入同输出，跨进程、跨词表版本可复现 |

两条工程属性：
- **Composability**：Processor 可插拔、Pipeline 可裁剪、Profile 可热替换
- **Degradability**：任一步骤失败返回 `Partial` 而非 error —— **永远不因规范失败而丢掉原文**

> 第 3、4、5、6 条是真正的护城河。Go 生态目前没有对标物。

## 6. 能力边界（明确不做）

| 不做 | 理由 |
|---|---|
| 分词 / NER / 词性 / 句法 | 无 NLP 模型，纯字符与词表；需要就在步骤 8 之前自接 |
| 词表的存储、同步、权限、生命周期 | Lexicon 是输入，**不是包的职责** |
| 从反馈中学习新变体 | 引擎不产生知识，只消费知识 |
| 流式 / 增量处理 | 当前整段幂等（可作为 v2 议题） |
| LLM 的成本与策略 | 包**提供扩展位**，不内嵌模型客户端；调用方注入实现 |

## 7. 典型应用场景（ASR 作为亮点场景展示）

包本身**领域中立**；下述场景中内置 8 步流水线**零配置即可用**：

| 场景 | 匹配的步骤 |
|---|---|
| ⭐ **语音转写后处理** | 全 8 步——噪音 + 口水词 + 同音字 + 编辑距离纠专名，几乎是为它量身定制 |
| **OCR 后处理** | 1、3、4、5、6（形近字变体 + 编辑距离 + 保护区） |
| **搜索 query 归一** | 3、4、5、6 + Suggest 分级做「你是不是要找」 |
| **工单 / CRM / 日志字段规范化** | 1、3、4 + 溯源（审计要求高） |
| **实体对齐前置** | 1~7 全跑，把变体归一后再做 entity resolution |
| **术语一致性检查（文档 / i18n）** | 只跑前 7 步、Suggestion 全量报告、不自动改 |

**ASR 场景在 README 的写法建议**：

> 通用语音识别模型**原理上不可能**认识你组织内部的人名、部门名、产品术语——
> 这类错误无法靠换更大的模型解决，只能靠外部知识注入。
> ark-lexnorm 提供的正是这条注入通道：给它一份 Lexicon，它把转写结果中的
> 噪声/口水词/同音字/近似字按确定性收敛到标准词，并告诉你每一处改了什么、
> 依据什么、有多确信、哪些它不敢改留给你决定。
> —— **微秒级、零第三方依赖、可复现、可审计。**

ASR 是「最有说服力的旗舰场景」，**不是定义本身**。
