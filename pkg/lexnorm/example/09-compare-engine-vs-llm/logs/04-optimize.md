## 总结论

基于本 example 的 PK 数据：

- **引擎擅长的领域**：
  - 标点/空格/口水词等纯机械清理（normalize + disfluency）
  - 词库内显式登记的变体（alias / correction / approximate）
  - 同音整词替换（如"袁梦莲"→"袁孟莲"，前提是 Variant{Homophone} 在词库显式登记）
  - 性能优势：单次 < 1ms vs LLM 2-5s
  - 成本优势：0 token vs LLM 每次 2-3K token

- **LLM 擅长的领域**：
  - 词库**未登记**但可上下文推断的同音/近似替换（如"五西辉"→"伍锡辉"、"菌种子"→"黑种子"）
  - 同音异字（如"羊城冰月"→"杨城冰月"、"扬城冰月"→"杨城冰月"）
  - 错字/口语化文本的语义识别
  - 但**风险**：可能误改（如"吴旭辉"→"伍锡辉"、"胜利群"→"佘丽群"）

- **核心优化建议**（按优先级）：

  1. **新增 `homophone` processor**：当前 Variant{Homophone} 类型没有任何 processor 消费。alias 只看 Alias，fuzzy 只看 Approximate，pinyin processor 按单字 pinyin 查表（不能消费 Variants）。这是工具包的明显能力空白。
  2. **`fuzzy` processor 的 confidence 默认值**：当前 `Variant.Confidence = 0` 时 silent skip（详见 fuzzy.go 注释）。建议给 Homophone 一个明确的默认值（如 0.85），便于调用方减少配置成本。
  3. **`pinyin` processor 增加整词模式**：当前只能按单字查 PinyinIndex，无法做"袁梦莲"→"袁孟莲"这类整词同音替换。建议新增 `pinyin-word` processor 或在现有 processor 加整词模式。
  4. **`disfluency` 阈值可配置**：当前"呃"→"" 是硬编码词表，建议支持业务自定义词表。
  5. **Pipeline 编排的"性价比排序"**：把高频高确定性 processor 放前面（normalize→alias→homophone→fuzzy→LLM），让 LLM 只处理低频低确定性 case，进一步降本。
  6. **abbrev variant 加最短长度保护**：transform 自动生成的 abbrev 如果 < 2 字容易误命中单字 token（如"大"→"大部门"），建议 builder 拒绝 < 2 字的 abbrev variant。

- **明确"不该做"**：

  - ❌ 不要让引擎学 LLM 的"上下文推断"逻辑（会破坏确定性架构不变量）
  - ❌ 不要把 LLM 加进 Standard Preset（D1 决策）
  - ❌ 不要给 alias/correction 引入模糊 conf（破坏"高确定性"语义）
