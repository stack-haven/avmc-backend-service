## 1. 总体设计（§53）

### Lexicon Build（O(Build)）

构建阶段一次性完成所有索引：

```text
Aho-Corasick
n-gram Index
ID Map
Immutable Snapshot
IntervalSet
Single-pass Replace
sync.Pool
```

### Runtime（O(1) / O(log n)）

运行期只读，零构建开销。

## 2. Aho-Corasick（§54）

### 用途

多模式匹配。

### 构建（Build 时）

```text
Trie
+
Failure Link
```

### 运行期

```text
Single Scan
```

### 复杂度

```text
构建：O(Σ pattern length)
匹配：O(N + matches)
```

### 禁止

```text
O(Entries × Text)
```

### 实现要点

- 文件位置：`lexicon/ahocorasick.go`
- 必须独立 fuzz + 与暴力实现做差分测试
- 公开 Matcher 接口供 Lexicon.Matcher() 返回

## 3. Fuzzy Matching（§55）

### 必须避免

```text
每个词条
 ×
每个字符窗口
 ×
Levenshtein
```

### 推荐流程

```text
n-gram Candidate
      ↓
Length Filter
      ↓
Distance
      ↓
Threshold
```

### 优化预期

| 优化点 | 效果 |
|---|---|
| n-gram 剪枝 | 候选数下降 > 95% |
| Length Filter | 进一步过滤 50%+ |
| Levenshtein 早停 | 单次比较常数下降 |

### 文件位置

- `match/ngram.go`：n-gram 倒排索引
- `match/levenshtein.go`：编辑距离（推荐 SIMD-friendly 一维实现）
- 两者均需 fuzz + benchmark

## 4. Single-pass Replace

### 旧实现问题

```text
R 次 strings.ReplaceAll → R 遍全文扫描
```

### 新实现

```text
单次左 → 右扫描
+ 最长匹配优先
+ 冲突消解
= 1 遍全文
```

### 实现要点

- 维护 `Original → Text` 的偏移映射
- 收集所有 hit（来自 Aho-Corasick + Fuzzy + ...）
- 按 Span.Start 升序排序
- 单次扫描合并应用
- 冲突时按 [11-确定性与匹配冲突消解](11-确定性与匹配冲突消解.md) §3 规则处理

### 文件位置

- `match/replace.go`

## 6. 热更新（§57）

### 实现

```go
type Store struct {
    current atomic.Pointer[Lexicon]
}

func (s *Store) Current() *Lexicon {
    return s.current.Load()
}

func (s *Store) Swap(newLex Lexicon) {
    s.current.Store(&newLex)
}
```

### 行为

```text
Old Request → Old Snapshot     // 旧请求持有的引用不被替换
New Request → New Snapshot     // 新请求取当前指针
```

**不阻塞**正常规范调用。

> 详见 [06-Lexicon与热更新](06-Lexicon与热更新.md) §6。

## 7. sync.Pool 复用

### 复用对象

- `*State`
- rune / byte buffer
- Change 临时构造缓冲

### 注意

- State 是 Request Scoped，从 Pool 取出的 State 必须清零
- Pool 仅降低分配，不影响正确性
- `-benchmem` 验证 alloc 次数

## 8. Benchmark 基线（§73）

### 必须覆盖

```text
Clean
Disfluency
Alias
Deterministic
Pinyin
Fuzzy
Context
Pipeline（端到端）
Engine（端到端）
```

### 目标基线

| 场景 | 目标 |
|---|---:|
| 45 字 / 2000 词条 | **< 200 µs** |
| 内存 | **< 32 KB** |
| allocations | **< 200** |
| 1000 字 / 10000 词条 | **< 3 ms** |

> 如果实际实现无法达到目标，应以 Benchmark 数据为准，
> **不得为了达到目标而虚构性能结论。**

### CI 回归

- 每次 PR 自动跑 Benchmark
- `benchstat` 对比基准
- 性能回退 > 10% 需明确说明

## 9. Profiling 工具

### 推荐

- `pprof`（`net/http/pprof`）
- `go test -bench -benchmem -cpuprofile`
- `go tool pprof` 分析热点
- `trace` 分析 Goroutine 调度

### 关注指标

- CPU：每个 Processor 的耗时占比
- Memory：State / Lexicon 的内存占用
- Allocations：每次 Normalize 的 alloc 次数
- Goroutine：是否有泄漏

## 10. 性能优化原则（§78 §9）

```text
Correctness
 ↓
Determinism
 ↓
Benchmark
 ↓
Optimization
```

### 禁止

- ❌ 为了性能牺牲 API 清晰度
- ❌ 在 Phase 1~8 提前优化
- ❌ 用 `unsafe` 绕过类型安全
- ❌ 用全局可变缓存破坏确定性
- ❌ 用 goroutine 并行化破坏确定性

### 允许

- ✅ Build 阶段预计算（O(Build) 换 O(1) Runtime）
- ✅ 缓存不可变结果（Lexicon 派生索引）
- ✅ sync.Pool 复用临时对象
- ✅ SIMD 友好的算法实现（须保留可读回退版本）
- ✅ Aho-Corasick / n-gram / IntervalSet 等成熟结构

---

## 11. 优化决策表

| 问题 | 算法级方案 | 工程级方案 |
|---|---|---|
| 多模式匹配慢 | Aho-Corasick | 预编译 |
| Fuzzy 慢 | n-gram 剪枝 | 长度过滤 |
| 解析目标慢 | ID Map（Build 时建） | O(1) Hash |
| Replace 重复扫描 | Single-pass + 偏移映射 | 合并 Apply |
| IsLocked 慢 | IntervalSet | O(log n) 二分 |
| Allocations 高 | sync.Pool + 字节比较 | 避免 string(rune[i:j]) |
| 词表大 | Lexicon Snapshot | 跨请求共享只读 |
