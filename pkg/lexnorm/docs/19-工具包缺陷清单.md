## 🔴 D-1: 变体是 canonical 子串时，alias 重复 canonical

**状态**：✅ **已修复（2026-09）**
**严重性**：🔴 P0（任何 dept 简称都触发，数据驱动即可复现）

**修复内容**：
1. `lexicon.Builder.Validate()`：拒绝 variant 为 canonical 子串（含相等）。
2. example `dept.json`：删除 4 个子串 variant（万康盛鼎/倍多客/倍多客测试/王德发）。
3. alias/fuzzy/deterministic：重复 variant 文本在构建匹配器时去重（消除双重审计）。
4. `State.Replace` 拒绝"包含已替换区间"的替换（防幻影审计，配套防御）。

### 复现

`data/dept.json`:
```json
{
  "id": "dept-1904450235179954177",
  "text": "万康盛鼎集团",     // canonical
  "variants": [
    { "text": "万康盛鼎", "kind": "alias", "confidence": 0.9 }  // ← 子串 variant
  ]
}
```

**测试**：T26/T26.2/T26.3/T08

### 现象

| 输入 | 引擎输出 | 期望 |
|---|---|---|
| `万康盛鼎集团开会` | `万康盛鼎集团集团开会` | `万康盛鼎集团开会` |
| `倍多客科技开发` | `倍多客科技科技开发` | `倍多客科技开发` |
| `王德发集团合作` | `王德发集团集团合作` | `王德发集团合作` |

### 根因

`processor/alias/alias.go::Process`:
```go
matches := p.matcher.Match(s.Original())
for _, m := range matches {
    // m.Start, m.End 是 variant 在原始文本中的位置
    canonical, ok := p.canonicalFor[m.Pattern]
    s.Replace(span, canonical, ...)
}
```

Aho-Corasick 扫描原始文本时，命中了 canonical 子串位置的 variant，然后 `Replace` 把它替换为完整 canonical——**破坏了原文本的 canonical 写法**。

引擎没有"variant 是 canonical 子串时不能应用"的防御逻辑。

### 建议修复方案（按 ROI 排序）

1. **Lexicon Builder 拒绝子串变体**（最简单，5 行代码）
   ```go
   // builder.go::Build
   for _, e := range entries {
       for _, v := range e.Variants {
           if strings.Contains(e.Text, v.Text) && v.Text != e.Text {
               return nil, fmt.Errorf("variant %q is a substring of canonical %q: %w", v.Text, e.Text, ErrInvalidConfig)
           }
       }
   }
   ```

2. **Alias processor 在替换前检查是否破坏 canonical**（更复杂，需 State.Text 位置比较）

3. **建议示例文档说明**：在 example README 中明确**不要登记 abbrev 子串变体**——本 example 已经在 `cmd/02-transform/pickAbbrev()` 限制 ≥ 2 字符，但**没考虑 2 字符的子串仍可能是 canonical 前缀**（如"倍多客"）。

### PR 准备材料

- 复现命令：`go run ./example/09-compare-engine-vs-llm/cmd/07-stress-test`
- 失败用例：T08、T26、T26.2、T26.3
- 日志位置：`example/09-compare-engine-vs-llm/logs/06-stress.log`

## 🟠 D-2: Variant{Homophone} 无人消费（文字与实际机制的偏差）

**状态**：✅ **已修复（2026-09）**
**严重性**：🟠 P1

**修复内容**：`processor/pinyin` 新增 **homophone 整词路径**：构建期把所有 `Variant{Homophone}.Text` 加入 Aho-Corasick 模式集（跳过 canonical 子串 variant），整词命中后按置信度阈值 Apply/Suggest/Skip。逐字路径改为只索引**单字 entry**（杜绝"1 字 span 换整词"的损坏隐患）。stress test 的自建管线已补入 pinyin processor。

### 现象

`data/system.json`:
```json
{
  "id": "term-heizhongzi",
  "text": "黑种籽",
  "variants": [
    { "text": "菌种子", "kind": "homophone", "confidence": 0.7 }  // ← homophone kind
  ]
}
```

引擎不识别 `菌种子 → 黑种籽`。

### 实测验证

最小复现 (单 entry + 1 variant{kind:homophone})，0 changes：

| Pipeline | 命中 |
|---|---|
| 只有 alias | ❌ 0 |
| 只有 fuzzy | ❌ 0 |
| 只有 pinyin | ❌ 0 |
| alias+fuzzy | ❌ 0 |
| alias+fuzzy+pinyin | ❌ 0 |

### 根因（精确）

| Processor | 是否消费 Variant{Homophone}.Text |
|---|---|
| `alias` | ❌ 只看 `VariantAlias` |
| `fuzzy` | ❌ 只看 `VariantApproximate` |
| `pinyin` | ⚠️ 只读取了 `Variant{Homophone}.Confidence`（用于 `defaultConfidence()`），**但不读 `Variant{Homophone}.Text`** |
| `deterministic` | ❌ 只看 `VariantCorrection` |
| **？** | **没人消费 Variant{Homophone}.Text** |

### PinyinProcessor 的“变向”机制

`processor/pinyin/pinyin.go::defaultConfidence(e)` 扫描 entry 的 variants，如果存在 Homophone，使用其 max confidence 作为 entry 默认 conf。

但 PinyinIndex 是在 builder.Build() 时**按 entry.Text 算拼音**的，不看 variants。因此：

1. 如果`袁孟莲`被登记 entry.text=“袁孟莲”+ variant{kind:homophone, text:“袁梦莲”}
2. builder 把“袁孟莲”的拼音 `yuan meng lian` 加进 PinyinIndex
3. PinyinProcessor 扫描“袁梦莲”时，对每**个汉字**算拼音，查 Index
4. 逐字 span（1 字）互相 overlap → State.Replace 静默拒绝
5. 结果：0 changes

所以原话“没人消费 Variant{Homophone}”严格上是“没人消费 Variant{Homophone}.Text”。

### 当前 workaround

本 example 把 kind 改成 `approximate`，让 fuzzy processor 接管。**但这违背 Variant 语义**：
- Homophone = 同音（不改变字）
- Approximate = 近似（编辑距离）
- “梦莲” vs “孟莲” 是不同字同音，是**同音不是近似**。但恰好编辑距离为 1，fuzzy 能误命中。
- “黑” vs “菌” 是**不同音**，homophone 不能表达其关系。

### 建议

1. **新增 `homophone` processor**（P1，本文档上一版未说明实现路径）
   - 消费 `Variant{Homophone}.Text`
   - 实现思路：在 Build 时同时为 **entry.Text 和 每个 Variant{Homophone}.Text** 建立 Aho-Corasick 模式集，Process 时扫描原文
   - 与 Alias/Fuzzy 的区别：提供语义上的"同音"标记，audit/交与业务语义更清晰

2. **新增 `asr-error` kind**（P2）
   - 专门表示“ASR 完全错读”（不同音）
   - 由 fuzzy processor 以较低 conf 处理

3. **架构不变量 I8 验证**：当前所有 processor 都应该按规范消费对应 kind

### PR 准备材料

- 复现命令：在 system.json 中登记 `kind: homophone` variant，观察不命中
- 失败用例：T04
- 详细实际机制见本节上半部分

## 🟡 D-3: 跨词边界识别

**严重性**：🟡 P2（场景有限，LLM 可兜底）

### 现象

文本：`"驾驶科金种籽"`
- 期望："驾驶科"识别为"加十个"的 ASR 错读，改为"加十个金种籽"
- 实际：引擎无法处理跨词错误

### 根因

Aho-Corasick 是 token-level 匹配器，不感知 token 之间的语义关系。

### 建议

- 新增 `Context` processor（消费 `Variant{Contextual}`）
- 利用 PinyinIndex + 上下文窗口推断
- 这是 LLM 兜底场景，无需 100% 解决

### PR 准备材料

- 复现命令：T17
- 大模型能处理（PK 报告 D 类）但脚本不能

## 🟡 D-4: 同姓歧义无消歧

**严重性**：🟡 P2

### 现象

公司有两个"龚"姓员工（龚千友、龚建军），文本"龚工"应该指谁？

- 当前：词库未登记"龚工"作为变体 → 不替换
- 期望：上下文消歧（"项目A 的龚工" vs "项目B 的龚工"）

### 建议

- 新增 `Context` processor（同 D-3）
- 或：在 example 内显式登记"建军工"作为龚建军的 variant（已实现）

### PR 准备材料

- 复现命令：T33
- 当前 workaround：手工登记带消歧后缀的 variant（如"建军工"）
