## 1. 总体架构（§3）

```text

│                 Application                  │
│                                              │
│ ASR / OCR / Search / CRM / Document / Other │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                    Engine                    │
│                                              │
│ Runtime / Profile / Lexicon / Pipeline       │
│ Middleware / Hook / Concurrency / Lifecycle │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                   Pipeline                   │
│                                              │
│ Processor → Processor → Processor → ...      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                  Processor                   │
│                                              │

                       │
                       ▼

│                                              │

```

### 核心关系

```text
Processor
    ▲
    │
Pipeline
    ▲
    │

```

> **Pipeline 本身也是 Processor。**（1.2 升级：Pipeline 现在是 interface，可由用户实现）

### 包结构硬约束

- **核心包（根 + `processor/*`）只能 import `lexicon/`、`internal/` 和 stdlib**
- **`lexicon/` 包独立**，不依赖任何上层对象，可独立 fuzz/benchmark
- **`hooks/otel/`**（如未来引入）必须使用**独立 go.mod（submodule）**，保持主模块零依赖
- **每个子包独立可读**：子包必须有自己的 `doc.go`

### 1.0 → 1.2 包结构变化

| 变化 | 原因 |
|---|---|
| 1.0 `match/` 独立子包 → 1.2 合并到 `internal/` | 匹配算法不对外暴露；internal 可独立测试 |
| 1.0 `processor/clean/` → 1.2 `processor/normalize/` | 名称更精确（与 NormalizeProcessor 对齐） |
| 1.2 新增 `runtime.go` / `option.go` / `call_option.go` 等 | Runtime Snapshot / Option 类型拆分更清晰 |
| 1.2 新增 `lexicon/source.go` / `compose.go` / `store.go` | LexiconSource / Compose / Store 三层抽象 |

## 3. 依赖方向（§49）

### 必须保持

```text
engine
  ↓
pipeline
  ↓
processor
  ↓
state
  ↓
lexicon / match
```

### 禁止反向依赖

| 反向依赖 | 状态 |
|---|:--:|
| `processor → engine` | ❌ |
| `processor → pipeline` | ❌ |
| `lexicon → engine` | ❌ |
| `match → processor` | ❌ |
| `match → engine` | ❌ |

> **审查工具**：`go list -deps github.com/stack-haven/lexnorm | grep -v "^github.com/stack-haven/lexnorm/" | grep -v "^internal/" | grep -v "vendor/"` 在 Phase 7 完成后必须只输出 stdlib 路径。

## 4. 第三方依赖（§50）

### 主模块

```text
github.com/stack-haven/lexnorm
```

**必须只依赖 Go Standard Library。**

禁止核心模块直接依赖：

```text
kratos
gorm
ent
redis
mysql
otel
LLM SDK
```

### 基础设施隔离

需要第三方基础设施时使用**独立 submodule**：

```text
github.com/stack-haven/lexnorm/hooks/otel   ← 独立 go.mod
github.com/stack-haven/lexnorm/hooks/redis  ← 独立 go.mod（若未来需要）
```

> **理由**：Go 生态标准做法（见 `otelhttp`）；让主模块保持零依赖是开源采纳率的第一杠杆。

## 5. Go 工程设计哲学（§51）

参考 Go-Kratos、Go Micro 等工程体系，但不依赖其代码。重点借鉴：

### 5.1 Interface First

```go
Processor
Lexicon
Hook
```

### 5.2 Dependency Inversion

高层依赖接口，不依赖实现。

### 5.3 Explicit Construction

```go
New(...)
WithLexicon(...)
WithPipeline(...)
WithMiddleware(...)
```

构造时必须显式注入，不允许从全局拉取。

### 5.4 Small Interfaces

Processor 保持：

```go
Name()
Process()
```

**避免巨大接口。**

### 5.5 Composition

通过：

```go
Pipeline(
    ProcessorA,
    ProcessorB,
)
```

组合能力。
