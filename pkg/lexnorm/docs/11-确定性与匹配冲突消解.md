# 11 · 确定性与匹配冲突消解

> 源节：§22 Match 冲突规则 · §23 Match 冲突示例 · §36 性能目标 · §49 Determinism
> 适用阶段：全阶段
> 受众：Reviewer（最常被违反的文档之一）
> 关键性：**确定性是 ark-lexnorm 的核心承诺之一**

---

## 1. 确定性原则

在以下条件一致时：

```text
Input
Profile
Lexicon Version
Processor Version
Processor Config
Pipeline Order
Runtime Snapshot
```

**必须得到可复现结果。**

> 1.2 强化：把 1.1 的 Runtime Snapshot 纳入确定性条件。
> 架构不变量 9：相同 Input + 相同 Snapshot 应产生确定性结果。

---

## 2. Match 冲突规则（**1.2 从 1.0 §63 补回**）

### 2.1 必要性

当多个候选在同一文本位置命中时，**必须**有确定的消解规则。否则：

- 同一个 Lexicon 在不同机器上得到不同结果
- 同一文本多次 Normalize 得到不同 Change
- A/B 测试无法复现
- 审计 / 回放失效

### 2.2 三层消解规则

#### 第一层：Longest Match First（默认）

```text
Longest Match First
```

#### 第二层：Higher Priority（相同长度时）

```text
Higher Priority
```

#### 第三层：Stable Lexicographical Ordering（仍相同时）

```text
Stable Lexicographical Ordering
```

### 2.3 冲突示例

#### 示例 1：长度不同

```text
Text:    "张三丰张"
Lexicon: [
    {Canonical: "张三丰", Priority: 1.0, Text: "张三丰"},
    {Canonical: "张三",   Priority: 1.0, Text: "张三"},
]

Result:
  命中 [0, 6) → "张三丰"   ← Longest 优先
  不命中 [6, 9) → "丰张"（或继续匹配）
```

#### 示例 2：长度相同、优先级不同

```text
Text:    "周丽群"
Lexicon: [
    {Canonical: "周丽群", Priority: 1.0, Text: "周丽群", Order: "1"},
    {Canonical: "周丽群", Priority: 0.8, Text: "周丽群", Order: "2"},
]

Result:
  优先 Priority=1.0 的 Entry
```

#### 示例 3：完全相同

```text
Text:    "周丽群"
Lexicon: [
    {Canonical: "周丽群", Priority: 1.0, Text: "周丽群", Order: "1"},
    {Canonical: "周丽群", Priority: 1.0, Text: "周丽群", Order: "2"},
]

Result:
  优先 Order = "1"（Stable Lexicographical / 注册顺序）
```

### 2.4 多 LexiconSource 冲突（Compose 时）

```text
Source A: 小田 → 田华 (Priority: 1.0)
Source B: 小田 → 田强 (Priority: 1.0)

→ 冲突！
→ Build 阶段返回 ErrConflict
→ 禁止静默覆盖
```

业务层必须明确优先级策略（如 Source 顺序、Pinned Version 锁定）。

---

## 3. 必须固定的因子

| 因子 | 固定方式 |
|---|---|
| Lexicon Ordering | Build 时按 `Canonical.Text` 字典序固化 |
| Candidate Ordering | 同一 Processor 内对候选排序，定义明确 tie-breaker |
| Match Conflict Resolution | §2 三层规则 |
| Pipeline Ordering | Pipeline 显式声明 |
| Processor Configuration | 配置校验 + Build 时固化 |
| Runtime Snapshot | Normalize 调用开始时锁定，不允许中途切换 |

---

## 4. 禁止依赖

```text
map iteration order      ❌
goroutine scheduling     ❌
random order             ❌
time.Now()               ❌（除作为 Duration 字段外）
外部 I/O                 ❌
```

### 实现要点

- Lexicon.All() 必须返回**确定顺序**（推荐字典序）
- 内部 candidate slice 必须显式 `sort.SliceStable`
- 内部 map 用于查找时，输出阶段必须再次排序
- 不可使用 `math/rand` 选 tie-breaker

### 特殊允许

- `time.Now()` 用于 `Result.Duration`、`Event.Duration` 等元数据，**不影响** Change 决策
- log/slog 的 timestamp 不影响 Result

---

## 5. Confidence 与确定性

Confidence 使用 `float64`，约定 `0.0 ≤ Confidence ≤ 1.0`。

### 越界处理

```text
Confidence = 1.5
   ↓
Config.Validate() → error
   ↓
New → ErrInvalidConfig
```

**不得静默 Clamp 到 0 或 1。**

### NaN / Inf 处理

- NaN → `ErrInvalidConfig`
- +Inf → `ErrInvalidConfig`
- -Inf → `ErrInvalidConfig`

> 详见 [10-配置校验与错误体系](10-配置校验与错误体系.md) §4。

## 6. 结果不可变原则

Result 对外表现为**值语义**。

```text
State (可变)
 ↓
Pipeline 完成
 ↓
Result Snapshot（不可变）
```

### 实现要点

| 要点 | 做法 |
|---|---|
| Result 类型 | 值类型（或返回时深拷贝内部 slice） |
| Result → State | 不持有 `*State` 引用 |
| Result.Ch | 返回只读副本 |
| Engine.Normalize 调用方 | 可并发读取同一 Result |

---

## 7. 决策确定性的完整链路

```text
Input
 ↓
Lexicon (Build 时排序固化)
 ↓
Matcher 扫描 (Aho-Corasick, 确定性输出)
 ↓
Candidate 收集 (sort.SliceStable)
 ↓
Match 冲突消解 (§2 三层规则)
 ↓
Decision (Apply / Suggest / Skip, 由 Config 阈值确定)
 ↓
Change (Applied=true/false, 顺序按 Span 升序)
 ↓
Result (值语义，不可变)
```

每一步都必须是**纯函数**（除 Duration 等元数据）。

---

## 8. 并发与确定性

### 允许

- 同一 Engine 多个 goroutine 并发 Normalize：**各自独立确定**
- 同一 Pipeline 多次 Process：**每次结果确定**
- 同一 Lexicon 跨请求共享：**只读，确定**
- 同一 Runtime Snapshot 跨 Process：**完全确定**

### 禁止

- 共享 State 跨 goroutine：违反单 Owner 约束
- 在 Process 中修改 Lexicon：违反 Read Only 约束
- 在 Process 中访问全局 map（写入）：违反确定性
- 在 Process 中切换 Runtime Snapshot：违反不变量 8

---

## 9. 调试与诊断

### 提供工具

- `Result.Changes`：完整 Apply + Suggest 列表
- `Result.Suggestions`：仅 Applied=false 的 Change
- `Result.Steps`：每步耗时
- `Result.Runtime`：完整运行快照（ProfileID + ProfileVersion + LexiconVersion + PipelineVersion + ProcessorVersions）
- `Change.Source`：人工登记 / 自动抽取 / 第三方
- `Change.RuleID`：命中的规则 ID
- `Change.EntryID`：命中的 Lexicon Entry ID
- `Change.Processor`：产生 Change 的 Processor 名称
- `Change.ProcessorVersion`：Processor 版本（用于重放）
- `Change.Reason`：决策依据（人类可读）

### Reproduce 协议

报告问题时必须提供：

```text
Input
ProfileID + ProfileVersion
LexiconVersion
PipelineVersion
ProcessorVersions
Processor Configs (YAML/JSON)
Pipeline Order
Result (Text + Changes + RuntimeInfo)
```

> 没有以上信息的问题报告**不予受理**。

## 10. LLM 与确定性（**D1 决议**）

LLM Processor 是天然非确定性能力。

### 处理原则

- LLM **不**在 Standard Preset 内（**D1 决议**）
- LLM Processor 必须**显式标识**其非确定性属性
- 业务配置决定是否启用 LLM
- 启用 LLM 后，`Result` 必须包含完整的 LLM 版本/模型信息（通过 `ProcessorVersion` 字段）
- 测试中如启用 LLM，应使用 mock 客户端或固定 seed

## 11. 自检清单

- [ ] 是否有 map 迭代直接参与输出？
- [ ] 是否有 goroutine 调度依赖（time.Sleep / channel）？
- [ ] 是否有 math/rand 用于 tie-breaker？
- [ ] Candidate slice 是否经过 sort.SliceStable？
- [ ] Confidence 越界是否静默 Clamp？
- [ ] Result 是否仍持有 *State 引用？
- [ ] Change 列表顺序是否确定？
- [ ] Match 冲突是否按 Longest → Priority → Lex 三层消解？
- [ ] Compose 多源冲突是否返回 ErrConflict？
- [ ] Runtime Snapshot 是否在 Normalize 期间被锁定？
